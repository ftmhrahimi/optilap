# مستند معماری زیرسیستم Crawler (اپتی‌لپ – MVP)

این سند همهٔ ماژول‌های خزندهٔ (Crawler) پروژهٔ اپتی‌لپ، وظیفهٔ هر ماژول و **دلیل انتخاب هر تصمیم** را توضیح می‌دهد.
هدف این است که هر کسی در تیم (Backend / AI / Frontend) بتواند بدون خواندن خط‌به‌خط کد، بفهمد این زیرسیستم چطور کار می‌کند و چرا این‌طور طراحی شده است.

مبنای این طراحی، سند معماری اصلی پروژه (`Optilap_MVP_V1.1.pdf`) است؛ به‌ویژه بخش ۷ (موتور Crawler)، بخش ۸ (Scoring Engine) و اصول طراحی بخش ۲.

---

## ۱. این زیرسیستم چه کاری انجام می‌دهد؟

ورودی: **نام یک قطعه** (مثلاً `LM358` یا `ATMEGA16A-AU`) یا یک فایل **BOM** اکسل.
خروجی: فهرستی از **پیشنهادهای فروش (Offer)** از سایت هر فروشنده، شامل:

- قیمت (به تومان و همچنین معادل ریالی برای مقایسهٔ بین فروشنده‌ها)
- وضعیت موجودی و تعداد موجود
- پکیج / فوت‌پرینت (مثل `TQFP-44`)
- نوع قطعه (`Original` / `Copy` / `Refurbished`)
- لینک محصول و زمان دقیق خزش (`crawled_at`)

این خروجی، ورودیِ مرحلهٔ بعد یعنی `referencePriceList` و سپس `Scoring Engine` است.

جایگاه این زیرسیستم در کل پایپ‌لاین:

</div>

```
BOM اکسل ──► Crawler (این زیرسیستم) ──► referencePriceList (PostgreSQL) ──► Scoring Engine ──► سبد بهینه ──► بازبینی اپراتور ──► خروجی Excel + ایمیل
```

## ۲. تصمیم‌های کلان طراحی و دلیل هرکدام

این بخش مهم‌ترین بخش سند است؛ چون «چرا»ها را روشن می‌کند.

### ۲.۱. چرا `requests` به‌جای Playwright؟
سند معماری در ابتدا Playwright را پیشنهاد داده بود، چون فرض بر این بود که فروشگاه‌ها «سنگین از نظر JavaScript» هستند.
اما وقتی سایت واقعی (جوان‌الکترونیک) را بررسی کردیم، مشخص شد که صفحات **سمت سرور رندر می‌شوند** (Server-Rendered)؛ یعنی یک درخواست سادهٔ HTTP کل HTML را با قیمت و موجودی برمی‌گرداند.
بنابراین طبق **اصل طراحی شمارهٔ ۱ سند («ساده‌ترین چیزی که کار کند، نه کامل‌ترین چیز ممکن»)** از `requests` استفاده کردیم چون:

- بسیار سریع‌تر است (یک BOM یعنی صدها بار بازکردن صفحه؛ مرورگر بی‌سر برای این حجم کند و سنگین است).
- وابستگی و پیچیدگی کمتری دارد.

با این حال، برای فروشنده‌های احتمالیِ آینده که واقعاً به اجرای JavaScript نیاز دارند، یک `PlaywrightFetcher` اختیاری هم نگه داشته‌ایم که **بدون تغییر در کد خزندهٔ فروشنده** قابل استفاده است.

### ۲.۲. چرا خزش «دو مرحله‌ای» (Two-Stage)؟
صفحهٔ نتایجِ جستجو در این سایت‌ها معمولاً **قیمت ندارد**؛ فقط **لینک محصول‌ها** را نشان می‌دهد. قیمت/موجودی/پکیج داخل صفحهٔ خودِ هر محصول است.
پس هر خزش دو مرحله دارد:

۱. صفحهٔ جستجو ► استخراج لینک محصول‌ها
۲. باز کردن هر صفحهٔ محصول ► استخراج قیمت/موجودی/پکیج/نوع

> نکته: نسخهٔ اول کد اشتباهاً فرض کرده بود قیمت روی خودِ صفحهٔ نتایج است (تک‌مرحله‌ای) و به همین دلیل «۰ نتیجه» برمی‌گرداند. اصلاح این موضوع، همان درسِ کلیدی این زیرسیستم بود.

### ۲.۳. چرا برای هر فروشنده یک خزندهٔ جدا؟
طبق **بخش ۷ سند**، ساختار HTML هر سایت متفاوت است. بنابراین هر فروشنده یک کلاس خزندهٔ مجزا دارد. اما برای اینکه دچار کپی‌کاری نشویم، منطق مشترک (پارس فارسی قیمت/موجودی) در یک «موتور استخراج» متمرکز شده و هر فروشنده فقط **سلکتورهای CSS مخصوص پلتفرم خودش** را اعلام می‌کند.

### ۲.۴. چرا کد **همگام (Synchronous)** است، نه async؟
چون `requests` همگام است و برای MVP کافی و ساده‌تر است. موازی‌سازی واقعی بعداً از طریق صف `Procrastinate` روی PostgreSQL (طبق سند) انجام می‌شود، نه با پیچیدگی `asyncio` در خود خزنده.

### ۲.۵. چرا وضعیت `ZERO_RESULTS` را از `ERROR` جدا کردیم؟
سند در بخش ۷ خواسته است سیستمی ساده برای **مانیتورینگ** داشته باشیم که وقتی یک خزنده مدام «صفر نتیجه» برمی‌گرداند (نشانهٔ تغییر ساختار سایت یا بلاک‌شدن) به تیم هشدار بدهد. برای همین «۰ نتیجه» یک وضعیت مستقل است، نه خطا.

### ۲.۶. چرا `crawled_at` و `price_rial` روی هر Offer ذخیره می‌شوند؟
- `crawled_at`: لازمهٔ **کشِ ساعتی** و **DataFreshnessScore** در سند است (قیمتِ زیر ۲ ساعت معتبر است).
- `price_rial`: چون بعضی سایت‌ها تومان و بعضی ریال نشان می‌دهند؛ برای اینکه Scoring Engine بتواند قیمت‌ها را با هم مقایسه کند، همه را به یک واحد مشترک (ریال) هم تبدیل می‌کنیم.

## ۴. توضیح ماژول‌به‌ماژول

### `normalize.py` — پاکسازی ارقام و قیمت فارسی
**کار:** تبدیل متن خام صفحه به عدد و مقدار تمیز.

- `normalize_digits`: ارقام فارسی (`۰۹`) و عربی (`٠٩`) و جداکننده‌ها (`٬ ، ٫`) را به معادل انگلیسی تبدیل می‌کند.
- `parse_price`: از متنی مثل `«۱٬۲۵۰٬۰۰۰ تومان»` مقدار عددی `1250000`، واحد پول (`IRT`=تومان / `IRR`=ریال) و متن خام را بیرون می‌کشد. متد `to_rial` تومان را ×۱۰ می‌کند.
- `detect_availability`: از عبارت‌های فارسی، «موجود/ناموجود» را تشخیص می‌دهد. (نکتهٔ ظریف: «ناموجود» شامل «موجود» است، پس اول حالت ناموجود چک می‌شود.)
- `normalize_part_query`: نام قطعه را برای جستجو تمیز می‌کند.

**چرا جدا؟** این منطق «قلب» درست‌کارکردن روی سایت‌های ایرانی است و باید مستقل و کاملاً تست‌پذیر باشد.

### `models.py` — مدل داده‌ها
سه چیز اصلی:

- `CrawlStatus`: یکی از `ok` / `zero_results` / `error`.
- `ProductOffer`: یک محصولِ پیدا‌شده با فیلدهای `vendor, part_query, title, product_url, price_amount, price_currency, price_rial, in_stock, stock_qty, package, part_type, crawled_at, ...`.
- `CrawlResult`: نتیجهٔ کامل یک خزش برای یک قطعه (وضعیت + فهرست Offerها + مدت‌زمان + خطا). متد `best_offer()` **ارزان‌ترین Offer موجود** را برمی‌گرداند.

**چرا Pydantic؟** چون Backend پروژه FastAPI است و این مدل‌ها مستقیماً به API و دیتابیس وصل می‌شوند و اعتبارسنجی نوع‌داده رایگان می‌گیریم.

### `fetch.py` — لایهٔ دریافت صفحه
- `HttpFetcher` (پیش‌فرض): یک `requests.Session` با هدر شبیه مرورگر و **Retry با Backoff نمایی** (۲، ۴، ۸ ثانیه) و رمزگذاری UTF-8. (Retry از الزامات بخش ۷ سند است.)
- `PlaywrightFetcher` (اختیاری): همان رابط `get_html` را دارد ولی با مرورگر بی‌سر؛ فقط برای فروشنده‌های JS-محورِ احتمالیِ آینده.

**چرا رابط مشترک `Fetcher`؟** تا خزندهٔ فروشنده اصلاً نداند صفحه با requests آمده یا مرورگر — جدا‌سازی مسئولیت‌ها.

### `extract.py` — موتور استخراج مشترک ⭐
مهم‌ترین ماژول از نظر معماری. همهٔ فروشنده‌ها از این استفاده می‌کنند:

- `collect_links`: از صفحهٔ جستجو، لینک محصول‌ها را (بر اساس سلکتور کارت محصول یا نشانهٔ URL) پیدا، یکتا و مطلق می‌کند.
- `find_price`: اول از سلکتورهای دقیق قیمت، بعد از کل متن صفحه، قیمت را می‌یابد.
- `find_stock`: موجودی و تعداد را از عبارت‌هایی مثل «موجود در انبار ۲۷» یا کلاس‌های `in-stock/out-of-stock` درمی‌آورد.
- `find_package` / `find_part_type`: پکیج و نوع را از جدول مشخصات یا برچسب‌های فارسی (`پکیج:`، `نوع قطعه:`) می‌خواند.
- `build_offer`: همهٔ این‌ها را کنار هم می‌گذارد و یک `ProductOffer` می‌سازد.

**چرا این ماژول وجود دارد؟** تا افزودن هر فروشندهٔ جدید فقط چند خط «سلکتور» باشد، نه بازنویسی منطق پارس. این همان چیزی است که اضافه‌کردن ۷ فروشندهٔ باقی‌مانده را سریع می‌کند.

### `base.py` — کلاس پایهٔ خزنده و مانیتورینگ
- `CrawlerConfig`: تنظیمات (timeout، تعداد retry، backoff، `max_products` = سقف صفحهٔ محصول در هر قطعه، `use_browser`).
- `BaseVendorCrawler`: کلاس پایه. متد `crawl()` گردش کار دو مرحله‌ای را مدیریت می‌کند و **هیچ‌وقت crash نمی‌کند** (خطا را به `CrawlResult` با وضعیت `error` تبدیل می‌کند). هر فروشنده فقط دو متد `find_product_urls` و `parse_product` را پیاده می‌کند.
- `FailureMonitor`: تعداد شکست‌های پشت‌سرهم هر فروشنده را می‌شمارد و پس از رسیدن به آستانه هشدار می‌دهد (الزام مانیتورینگ بخش ۷).

### `vendors/` — خزندهٔ هر فروشنده
هر فایل فقط سه چیز را مشخص می‌کند: نام/آدرس/الگوی جستجو، سلکتورهای لینک، و سلکتورهای قیمت/موجودی.

| فایل | فروشنده | پلتفرم | وضعیت |
|---|---|---|---|
| `javanelec.py` | JavanElectronic | ASP.NET Core | **روی سایت واقعی تأیید شد** |
| `eca.py` | ECA | PrestaShop | سلکتورهای استاندارد — نیاز به کالیبراسیون روی سایت واقعی |
| `micromodern.py` | MicroModern | WooCommerce | سلکتورهای استاندارد — نیاز به کالیبراسیون روی سایت واقعی |

نکتهٔ جوان‌الکترونیک: چون صفحهٔ محصول اول قیمتِ خط‌خورده و بعد قیمت نهایی را نشان می‌دهد، عمداً سلکتور قیمت خالی گذاشته شده تا از کل متن **آخرین عدد تومانی** (قیمت نهایی) گرفته شود.

### `registry.py` — فهرست ثابت فروشنده‌ها
طبق سند، MVP یک **فهرست ثابت ~۱۰ فروشنده** دارد. این فایل نام هر فروشنده را به کلاس خزنده‌اش نگاشت می‌کند. `get_crawler("ECA")` و `all_vendor_names()`.

### `bom.py` — خواندن فایل BOM
`read_bom` فایل اکسل را می‌خواند و ستون شمارهٔ قطعه/تعداد/پکیج را **با تطبیق انعطاف‌پذیر عنوان ستون** پیدا می‌کند (چون هر مشتری عنوان‌های متفاوتی می‌گذارد). `unique_parts` قطعات یکتا را برمی‌گرداند.

### `scripts/` — ابزارهای اجرایی
- `crawl.py`: ابزار خط فرمان. یک قطعه یا کل BOM را می‌خزد و **همهٔ Offerها** را در یک جدول نشان می‌دهد (Vendor/Price/Stock/Package/Type/Time/Title + لینک). با `--out` خروجی JSON می‌دهد و با `--best` فقط بهترین را. (خروجی UTF-8 شده تا روی ویندوز با متن فارسی crash نکند.)
- `inspect_site.py`: ابزار عیب‌یابی/کالیبراسیون. لینک‌های پیدا‌شده و پارسِ اولین محصول را چاپ می‌کند تا سلکتورهای هر سایت را با HTML واقعی تنظیم کنیم.

### `tests/` و `fixtures/`
تست‌های خودکار (بدون اینترنت) که با HTMLهای نمونه صحت پارس قیمت/موجودی/لینک را تضمین می‌کنند. اگر بعداً کدی خراب شود، تست فوراً می‌گیرد.

## ۶. خروجی و اتصال به مرحلهٔ بعد

- خروجی واقعیِ خزنده، **آبجکت‌های `CrawlResult`/`ProductOffer` در حافظه** هستند.
- فایل JSON فقط برای بازبینی/دیباگ است، نه رابطِ اصلی پایپ‌لاین.
- **مرحلهٔ بعد طبق سند:** نوشتن این Offerها در **PostgreSQL** (جدول `referencePriceList`) با قانون **کشِ ۲ ساعته**، و سپس خواندن آن توسط Scoring Engine. فیلدهای `ProductOffer` دقیقاً همان ستون‌های موردنیاز جدول را دارند، پس این گذار کوچک و تمیز خواهد بود.

## ۷. نگاشت نیازمندی‌های سند معماری به کد

| نیازمندی سند | کجای کد |

| خواندن BOM اکسل مشتری | `bom.py` |

## ۸. کارهای باقی‌مانده (فازهای بعدی)

1. **کالیبراسیون ECA و MicroModern** روی سایت واقعی با `inspect_site.py` (سلکتورها بر پایهٔ استاندارد PrestaShop/WooCommerce نوشته شده‌اند).
2. **افزودن ۷ فروشندهٔ باقی‌مانده** از `Vendors_V1.0.xlsx` (هرکدام چند خط سلکتور).
3. **لایهٔ ذخیره‌سازی PostgreSQL** + جدول `referencePriceList` + قانون کشِ ۲ ساعته.
4. **صف `Procrastinate`** روی PostgreSQL برای اجرای دوره‌ای و موازی (طبق سند).
5. اتصال به **Scoring Engine** و در نهایت خروجی **Excel + ایمیل**.

## ۹. راهنمای افزودن یک فروشندهٔ جدید

</div>

```python
# optilap_crawler/vendors/newvendor.py
from bs4 import BeautifulSoup
from .. import extract
from ..base import BaseVendorCrawler
from ..models import ProductOffer

class NewVendorCrawler(BaseVendorCrawler):
    vendor_name = "NewVendor"
    base_url = "https://example.ir"
    search_pattern = "https://example.ir/search?q=[PART_NAME]"

    def find_product_urls(self, search_html):
        soup = BeautifulSoup(search_html, "html.parser")
        return extract.collect_links(
            soup, self.base_url,
            card_selectors=[".product-card"],     # سلکتور کارت محصول
            link_selectors=["a.title"],            # لینک داخل کارت
            url_markers=["/product/"],             # نشانهٔ URL محصول (پشتیبان)
        )

    def parse_product(self, html, url, part_query):
        return extract.build_offer(
            vendor=self.vendor_name, base_url=self.base_url,
            part_query=part_query, url=url, html=html,
            price_selectors=[".price"],            # سلکتور قیمت
            stock_selectors=[".stock"],            # سلکتور موجودی
        )
```
